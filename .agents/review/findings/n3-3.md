# n3-3: The Linux permission remedy is absent from end-user artifacts

**Severity**: HIGH — raised by the 2026-07-25 `openreview codex` pass
over `16901d8..abf32d7`.
**Status**: Verified
**Branch**: `neon-80-support` (worked in place)
**Commit**: see the `n3-3:` commit

## Evidence

packaging/am_configurator.spec:54 — the native data list omits the udev rule; packaging/linux/build_appimage.sh:44 copies only that frozen bundle, and the wheel configuration packages only am_configurator. The rule exists only in the source archive despite the runtime message naming packaging/linux/60-am-neon-80.rules.

## Predicted observable failure

AppImage and wheel users encountering the normal Linux permission failure are instructed to copy a file they do not possess, leaving Neon 80 access unusable without separately finding the source repository.

## What

The guard I wrote asserted only that `/packaging/` is on the sdist allowlist,
which made the omission look covered. A test that checks the wrong artifact is
worse than no test.

## Approach

The rule moved from `packaging/linux/` into the package at
`am_configurator/data/60-am-neon-80.rules`, so it travels with the code rather
than with the source tree. Three delivery paths now carry it: the wheel (via a
hatch `artifacts` pattern, because `packages` alone does not carry non-Python
files), the PyInstaller bundle the AppImage wraps (via `datas`), and the sdist
(unchanged, under the existing allowlist).

`udev_rule_path()` resolves the installed location at runtime and the permission
message prints it, so the user is told where the file actually is on their
machine rather than where it sits in a repository they may not have.

The reviewer's suggestion: Bundle the rule at a stable runtime-accessible location in the wheel and AppImage, provide an actionable installation flow, and test the finished artifacts rather than only the sdist allowlist.

## Reopen round 1 — 2026-07-25

`codereview codex` returned **reopened**, correctly, and on precisely the users
this finding was about.

Shipping the rule inside the package was right, but the instructions told the
user to resolve its path with
`python -c "from am_configurator.hid_transport import udev_rule_path; ..."`.
That cannot work for an AppImage user: the package lives on a temporary mount
that vanishes when the application exits, and the shell's Python has no such
module to import. So the remedy still failed for the delivery path the finding
was raised about.

Repair: the application prints the rule's **contents** on stdout via a new
`--print-udev-rule` flag, which behaves identically for an AppImage, a wheel,
and a source checkout:

    sudo ./AM_Configurator.AppImage --print-udev-rule > /etc/udev/rules.d/60-am-neon-80.rules

The runtime permission message now names that flag instead of a path, and the
documentation gives the AppImage and wheel invocations separately.

Guard: `test_the_rule_is_obtainable_without_a_filesystem_path` runs
`desktop.main(["--print-udev-rule"])` and asserts the rule text reaches stdout,
and asserts the documentation no longer instructs a path resolution. Restoring
the `python -c` guidance fails it. Verified, then restored.
