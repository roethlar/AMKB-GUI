# cl-14: Queued media render can mutate a workspace that left Source

**Severity**: MEDIUM — an ordinary tool switch can make delayed media work stop
unrelated Board playback without an error or user action.
**Status**: Open
**Branch**: —
**Commit**: —

## Evidence

- `am_configurator/web/app.js:3238-3260` validates only draft identity and
  revision before dispatching `SEQUENCE_RENDER_STARTED`.
- `am_configurator/web/lighting_workspace.js:807-825` handles that event by
  stopping playback and advancing the preview request epoch unconditionally.
- `am_configurator/web/app.js:3275-3290` checks route, tool, destination, and
  media ownership only after preview-session acquisition; its discard changes
  the media draft but does not terminate the workspace request it already
  started.
- `am_configurator/web/lighting_composer.js:122-171` permits one running task
  plus one latest queued task. The queued task can begin well after the user
  leaves Source.
- `am_configurator/web/app.js:2563-2568` changes studio tools without
  cancelling queued media work.

The reviewed range was independently traced after intake. A queued task retains
the same catalog ID and draft revision across `TOOL_SELECTED`, so its initial
guard passes even though Source no longer owns the workspace.

## Predicted observable failure

Queue a second framing render behind a slow full GIF render, switch to Paint or
Effects, and start Board playback. When the queued render begins, playback
stops and the play button returns to Play. The discarded request can also leave
the current preview marked updating with no matching terminal completion.

## What

The scheduler correctly prevents overlapping full renders, but task ownership
is checked after the task has already mutated the shared workspace. Tool
transitions do not cancel pending media work.

## Approach

Reject a queued request against exact route, tool, destination, and media
identity before dispatching any render-start event. Cancel pending media
scheduler work whenever the user leaves Source; an already-running request
remains harmless because its captured context cannot publish after the
transition. If an exact current request is discarded after it starts, terminate
that request through a reducer-owned event rather than leaving preview state
updating.

## Files changed

Planned repair scope will be frozen before implementation. Expected production
surface is `am_configurator/web/app.js` and, only if a terminal discard event
is required, `am_configurator/web/lighting_workspace.js`; guards belong in
their matching browser tests and the native media-framing audit.

## Guard proof

Required behavioral proof: hold one full render in flight, queue a second
revision, leave Source, start Board playback, release the first render, and
prove playback continues while no stale request changes preview status.
Reverting the ownership/cancellation repair must make that check fail.

## Coder dispute (if any)

None. The task mutates workspace state before evaluating the predicate that
would reject it.

## Known gaps

The selected-frame/full-sequence two-tier scheduler is separately tracked by
`cl-16`; this repair must remain valid after that scheduler is wired.
