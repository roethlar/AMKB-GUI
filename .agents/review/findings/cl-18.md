# cl-18: Corrupt remembered layout evidence cannot self-heal

**Severity**: MEDIUM — one damaged private layout-evidence file permanently
disables remembered offline geometry while the UI recommends a recovery action
that cannot repair it.
**Status**: Verified
**Branch**: —
**Commit**: `8e059292411b85a3387d348c8a4ee36ef8137f25`

## Evidence

- `am_configurator/store.py:205-216` rejects oversized, undecodable, or
  non-object persisted layout evidence.
- `am_configurator/store.py:228-239` loads that existing file before it can
  construct and atomically write replacement evidence, so the same exception
  prevents every repair attempt.
- `am_configurator/store.py:243-248` retains arbitrary dictionary entries by
  signature inequality without proving they remain valid evidence.
- `am_configurator/profile_metadata.py:180-186` rejects the entire remembered
  set when any retained entry fails strict validation.
- `am_configurator/profile_metadata.py:225-234` tells the user to connect and
  read the keyboard, while `am_configurator/server.py:1519-1526` swallows the
  failed persistence attempt made by that path.

The intake reproduction created valid remembered evidence, truncated its
private JSON file, confirmed resolution returned no evidence, then attempted to
remember the same live layout again. The write raised `JSONDecodeError` before
replacement and left the store unrecovered.

## Predicted observable failure

After a crash, partial write, manual damage, oversize file, or one invalid
retained entry, every legacy Neon profile loses offline Per-key geometry. The
user can repeatedly follow the instruction to connect and read the keyboard,
but the private file never heals; recovery requires knowing and manually
deleting an internal application file.

## What

Read-time refusal is correct, but write-time recovery incorrectly treats
untrusted prior bytes as a prerequisite for storing newly validated live
evidence. Invalid retained entries can also poison an otherwise writable set.

## Approach

Keep corrupt persistence unusable for layout resolution. At the write boundary,
treat an unreadable or invalid prior collection as empty, retain only entries
that pass the same strict evidence validation, and atomically replace the file
with the newly validated layout plus valid bounded history. The recovery
instruction then describes an action the application can actually complete.

## Known gaps

An externally hand-forged private file containing two individually valid
entries with the same non-current signature remains read-invalid and may retain
that duplicate pair during a later repair write. Application-written files
cannot create this state because every write deduplicates the current
signature. The independent reviewer accepted `cl-18` without expanding it to
this unapproved, private-file tampering case.
