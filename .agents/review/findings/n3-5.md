# n3-5: Device-controlled XZ data has no decompressed-size bound

**Severity**: MEDIUM — raised by the 2026-07-25 `openreview codex` pass
over `16901d8..abf32d7`.
**Status**: Verified
**Branch**: `neon-80-support` (worked in place)
**Commit**: see the `n3-5:` commit

## Evidence

am_configurator/hid_transport.py:220 — lzma.decompress expands the entire keyboard-supplied blob; the preceding limit constrains only its compressed size.

## Predicted observable failure

A malformed or hostile Vial definition can expand a small allowed payload into enough data to freeze or exhaust the application's memory during discovery.

## What

The cap I added bounds the wrong quantity. Discovery runs against any attached
board, so this is reachable without a write.

## Approach

`_decompress_bounded` decompresses incrementally with an explicit 1 MiB output
ceiling and rejects a stream that is truncated or carries trailing data. The
compressed cap stays as a cheap first filter; it simply is not the bound that
matters.

The reviewer's suggestion: Use incremental decompression with a small explicit output ceiling, reject trailing or incomplete streams, and apply an overall deadline to definition retrieval and decoding.

exercised `_decompress_bounded` directly, so reverting `fetch_definition` to a

nothing proved the call site used it. That is the same non-load-bearing pattern

drives the bomb through `fetch_definition`; reverting the call site now fails it
with `'expands beyond' not found in "The keyboard's definition is not valid
JSON."`. Verified, then restored.

## Coder dispute (if any)

None. Admitted and **verified empirically**: `lzma.compress(b'\x00' * 200 MiB)`
produces 30,644 bytes, which passes the 64 KiB compressed-size cap and then
expands to 200 MiB.
