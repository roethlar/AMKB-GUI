# n3-4: hidapi open failures cannot be classified by exception text

**Severity**: MEDIUM — raised by the 2026-07-25 `openreview codex` pass
over `16901d8..abf32d7`.
**Status**: Verified
**Branch**: `neon-80-support` (worked in place)
**Commit**: see the `n3-4:` commit

## Evidence

am_configurator/hid_transport.py:156 — classification searches OSError text for permission or busy words, but the locked hidapi 0.15 binding reports every open_path failure as the generic 'open failed'.

## Predicted observable failure

Permission-denied and busy devices are reported as detached, so Linux users never see the udev remedy and users cannot distinguish contention from absence.

## What

Every open failure is therefore reported as 'The keyboard is no longer
attached.' On Linux the udev remedy — the entire point of N3c — is unreachable.

## Approach

`_classify_open_failure` inspects the device node instead of the exception text.
On Linux the path is a `/dev/hidraw*` node: missing means absent, present but
not accessible means permission (with the udev remedy), present and accessible
means something else holds it. Elsewhere the path is an opaque OS handle with
nothing to inspect, so the error says the cause could not be determined rather
than asserting one — a re-enumeration still distinguishes a vanished device.

The reviewer's suggestion: Use errno-bearing platform preflight where available, re-enumeration or backend-specific diagnostics elsewhere, and return a truthful generic unavailable error when the cause cannot be distinguished.

## Guard proof

`tests/test_hid_transport.py::OpenFailureClassificationTests`.

`test_the_binding_really_does_hide_the_cause` pins the premise against the real
hidapi, so a future version that reports errno will surface here rather than
leaving this workaround in place unexamined.

`test_open_routes_failures_through_the_classifier` guards the call site. The
first version of this guard was vacuous in exactly the way n3-5's was: it
exercised `_classify_open_failure` directly, so reverting `_open` to substring
matching left every test green. Reverting the call site now fails.

User-visible difference, demonstrated directly: on a Linux box with the node
present and inaccessible, the old code produced `HidDeviceAbsent: The keyboard
is no longer attached.` and the new code produces `HidPermissionDenied` naming
the udev rule.

`codereview codex` returned **reopened**, correctly: if the fallback
re-enumeration raised, the raw exception escaped instead of the promised generic
`HidError`. `identify` catches only `HidError`, so one flaky USB read would have
crashed discovery for every device rather than marking one unidentified.

Repair: the re-enumeration is wrapped, and the function's contract — *return* an
error, never raise one — is now stated in the code.
`test_the_classifier_never_raises_even_if_enumeration_fails` and
`test_discovery_survives_an_open_failure_with_broken_enumeration` guard it;
removing the wrap makes both error.

One guard needed fixing too: it patched `_open`, which is the function that
converts the `OSError`, so it bypassed the behaviour under test. It now patches
the hidapi binding underneath.
