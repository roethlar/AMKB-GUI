# cl-10: Lowercase profile colors blank the Lighting Studio

**Severity**: HIGH — a profile accepted by backend validation, including one
saved by an earlier application build, can open with an empty black Lighting
Studio and no working playback or scrubbing.
**Status**: In progress
**Branch**: —
**Commit**: pending

## Evidence
At reviewed head `1ee73a81182c8f401b1942776d3df7c005541f33`,
`am_configurator/web/lighting_workspace.js:9,173-178` accepts only uppercase
`#RRGGBB` input and throws `invalid_color` before any Board projection.
`am_configurator/server.py:261-268,1397-1398` accepts hexadecimal digits in
either case, and the parent application default at
`cbf1346070fb908bd932028508f3c43923fe0057:am_configurator/web/app.js:64`
is lowercase `#8358ff`. Global file import normalizes colors, but CLI-loaded,
Library-opened, stored, and already-open documents can reach the new workspace
constructor without that import-only normalization.

## Predicted observable failure
Open a previously saved profile whose frame colors contain lowercase hex.
`currentLightingBoardFrameSet()` throws during `renderLightingEdit()`, which
reports one workspace error and leaves no accepted Board projection. The frame
list says there are no frames, LEDs are black, and playback and scrubbing have
nothing to operate on even though backend validation says the document is
valid.

## What
The new canonical Board contract confuses canonical output with accepted input.
It correctly requires every published Board color to be uppercase, but rejects
a losslessly equivalent spelling already accepted and emitted by supported
application paths.

## Approach
Keep uppercase as the only `BoardFrameSet` representation while accepting
case-insensitive six-digit hexadecimal input at the constructor boundary.
Normalize each accepted color to uppercase before freezing the frame. Preserve
all existing rejections for wrong types, lengths, prefixes, and non-hex digits.
