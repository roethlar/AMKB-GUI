# cl-15: Linux picker hides uppercase supported media extensions

**Severity**: MEDIUM — valid GIF, PNG, and BMP files can be invisible and
unselectable in the Linux native picker solely because their extension uses
uppercase letters.
**Status**: Verified
**Branch**: —
**Commit**: `027f2eb18cedd88974ae5a965de2176c0690f801`

## Evidence

- `am_configurator/desktop.py:133` supplies only
  `*.gif;*.png;*.bmp` patterns to the native dialog.
- `am_configurator/desktop.py:201-225` passes that sole filter to
  PyWebView's `create_file_dialog`.
- Pinned PyWebView 6.2.1's GTK backend, `webview/platforms/gtk.py:611-620`,
  passes each pattern directly to `Gtk.FileFilter.add_pattern`; GTK pattern
  matching is case-sensitive and the backend adds no fallback filter.
- `tests/test_desktop.py::test_media_chooser_filters_supported_formats_and_returns_no_path`
  checks only lowercase patterns.
- The native media audit injects `_AuditMediaBridge`, so it validates the
  application workflow but intentionally cannot exercise the operating-system
  dialog filter.

The current installed backend was inspected after intake and matches the
reviewer's cited direct `add_pattern` loop.

## Predicted observable failure

On Linux, files such as `ANIM.GIF`, `LOGO.PNG`, and `SPRITE.BMP` do not
appear in the Add media dialog and cannot be selected. Renaming the file
outside the application is the only workaround.

## What

The filter assumes extension matching is case-insensitive. That is true for
the Windows and macOS dialog backends but not for WebKitGTK's GTK file filter.

## Approach

Include lowercase and uppercase patterns for every supported media extension.
Keep the decoder and byte bounds authoritative after selection; this changes
discoverability only and admits no new format. Guard the exact case variants in
the desktop bridge test, with later Linux native qualification retaining the
real-dialog acceptance responsibility.
