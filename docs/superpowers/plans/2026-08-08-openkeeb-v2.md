# OpenKeeb v2 — broad custom-keyboard platform

**Status:** Planning only on branch `v2/openkeeb`, created at planning commit
`59f0bb1`. The owner approved OpenKeeb as the public name for an in-place
`2.0.0` successor to AM Configurator. No source rebrand, identifier migration,
implementation, push, or release is authorized yet. The next required owner
ruling is the OpenRGB dependency policy below.

## Settled product identity

- Public name: **OpenKeeb**.
- Release lineage: existing repository and signed release machinery.
- Install lineage: retain the shipped Windows installer `AppId` and macOS
  bundle identifier so v2 is an upgrade, not a side-by-side product.
- Publisher identity: retain existing Apple Developer ID/notarization and
  Azure Trusted Signing accounts.
- History: AM Configurator 0.x tags, releases, filenames, and copy stay as
  published history.
- Unpublished namespaces: AUR and Flatpak publication is paused until new
  OpenKeeb identifiers are owner-approved.
- Internal implementation names may remain `am_configurator` when changing
  them has no user benefit. Public aliases and migration behavior need an
  explicit slice.
- Name clearance: exact namespace, domain, and legal/trademark checks gate
  public v2 branding. The preliminary 2026-08-08 scan found no exact AUR
  package and two small GitHub repositories named `openkeeb`; that is evidence
  to investigate, not legal clearance.

## Objective

Turn the current family-specific configurator into a capability-composed local
desktop application for practical custom-keyboard coverage:

- keymap and macro editing on standards-compatible boards even when they have
  no controllable RGB;
- Lighting Studio output on boards that expose safe per-LED or effect controls;
- persistent on-device animation only when the device protocol really supports
  it;
- explicit unavailable capabilities instead of pretending every keyboard has
  feature parity;
- existing Angry Miao families remain supported without behavior regressions.

"Any custom keyboard" is an aspiration bounded by discoverable identity,
documented or safely derived protocols, usable layout evidence, and hardware
verification. It is not a claim that arbitrary proprietary firmware can be
driven automatically.

## Settled compatibility contract

OpenKeeb support is capability-based (owner approval, 2026-08-08):

- keymap, macros, live lighting, hardware effects, and persistent custom-frame
  upload are independently discoverable and supportable;
- a board may be publicly supported for a strict subset, with unavailable
  surfaces explicitly disabled rather than guessed;
- every claim is model/revision/firmware and capability specific until broader
  equivalence is proven;
- host-driven live lighting is never represented as persistent on-device
  storage;
- every mutation keeps exact identity matching, full preflight, typed
  confirmation, and manual hardware qualification.

This contract preserves Neon's already-shipped full parity without imposing
that historical board-specific threshold on new v2 devices.

## Current architecture and constraints

- `transport.DeviceTransport` dispatches a complete device driver by transport
  kind. It currently registers the shared Angry Miao serial driver and one
  Neon-specific raw-HID driver.
- `device_mapping.FamilySpec` combines transport, frame limits, macro limits,
  key matrix, and lighting geometry under a monolithic family identifier.
- browser `lighting_targets.js` mirrors the family table; `app.js` still owns
  hardcoded family labels and physical layouts.
- Vial keymap and macro codecs are reusable, but discovery and layout evidence
  are currently gated specifically to Neon 80.
- Lighting Studio already consumes server-published raster geometry for newer
  paths, which is the seam for non-Angry-Miao lighting providers.
- Writes require model matching and typed confirmation. Automated tests and
  smoke tests must never write to a physical keyboard.
- The existing sanitized support-report builder/API is read-only groundwork;
  its UI slice must use the v2 capability model.

## Protocol lanes to prove

### Vial

Target self-describing Vial devices first for generic keymap and macro support.
The device-supplied definition can provide identity, matrix, and physical
layout evidence. Treat definition data as untrusted input with size, shape,
coordinate, and key-count bounds. Vial does not imply arbitrary persistent RGB
animation support.

### VIA/QMK dynamic keymap

VIA firmware exposes dynamic keymap and macro commands but normally needs an
external trusted keyboard-definition JSON for physical layout and options.
First support user-imported, validated definitions; a remote/bundled catalog is
separate because provenance, updates, and definition licensing must be settled.
QMK firmware without VIA/Vial/XAP runtime support is not dynamically writable
merely because its source is QMK.

### XAP

Treat QMK XAP as an experimental adapter and research spike, not a broad claim.
It is relevant to Drop CTRL/ALT and exposes structured subsystems including
RGB-matrix configuration, but upstream protocol/client maturity, exact firmware
on the owner's boards, and source licensing must be verified before reuse.

### OpenRGB

Use OpenRGB's versioned local SDK as the first candidate for cross-vendor live
lighting. It can expose device type, LED lists, zones, matrix maps, modes, and
per-LED updates. OpenKeeb must distinguish:

- `live_stream`: Studio playback is host-driven and stops when the service or
  application stops;
- `hardware_effect`: configure a firmware-defined mode/color/speed;
- `persistent_upload`: device stores OpenKeeb-authored frames independently.

Never label a live stream as saved to the keyboard. Match an OpenRGB controller
to the same physical device conservatively; ambiguous multi-device matches are
read-only until the user binds them.

### Vendor adapters

Use only when a target lacks an adequate standard lane or exposes materially
better persistent lighting. Each adapter needs protocol provenance, license
review, read-only discovery, exact model gating, fake-transport tests, and
physical hardware qualification. Mountain keymapping is likely such a separate
problem even if OpenRGB covers its lighting.

## Target architecture

Represent one physical keyboard as an identity plus independently provided
capabilities, not one transport-shaped family driver:

```text
KeyboardIdentity
  endpoints: USB interfaces / serial ports / local service controllers
  evidence: VID/PID, protocol identity, definition hash, connection token
  capabilities:
    KeymapProvider?   read / validate / write / limits / encoding / layout
    MacroProvider?    read / validate / write / byte and slot limits
    LightingProvider? targets / geometry / output mode / plan / write-or-stream
```

Introduce a device graph that correlates multiple endpoints belonging to one
physical board. Correlation evidence must be explicit and ranked; never join
two same-model keyboards solely by VID/PID or product string. A user-confirmed
binding may be stored only with non-secret stable identifiers and must be
invalidated when endpoint evidence changes.

Capability providers must expose validation/preflight separately from mutation.
All validations for a user action complete before the first byte is sent. A
composed action spanning providers is not atomic; UI and receipts must identify
exactly which capability changed and report partial failure honestly.

## Provisional implementation slices

These are not approved for implementation. Revise after the owner decisions.
Each landed slice is one commit with its tracker/state update in the same
commit.

### V2-0 — Identity and migration contract

- Set public namespaces and branch/release policy.
- Inventory every display name, command, package id, settings path, bundle id,
  installer id, URL, artifact filename, and signing assertion.
- Design v1 settings/profile migration and rollback before changing names.
- Prove existing signed release workflow can build renamed artifacts with the
  retained signing and install identities.

### V2-1 — Capability model, behavior-neutral

- Split `FamilySpec` into identity plus optional keymap, macro, and lighting
  descriptors.
- Split `DeviceTransport`'s all-features protocol into provider protocols.
- Project capabilities through `/api/devices` and browser state.
- Render existing four families identically; no new hardware support.
- Red-proof every refactor against the full existing family suite.

### V2-2 — Generic Vial keymap and macros

- Generalize read-only Vial discovery beyond Neon's hardcoded identity without
  weakening Neon's write gate.
- Validate dynamic definition/layout evidence and device-reported limits.
- Reuse the QMK/Vial codecs behind generic providers.
- Pilot one exact non-Neon Vial device; qualify read, edited write, read-back,
  unplug/replug identity invalidation, and two-same-model ambiguity behavior.

### V2-3 — VIA definition-backed keymap and macros

- Define a bounded internal definition schema and importer for a user-supplied
  VIA JSON.
- Match definition identity to a connected device and protocol version before
  enabling writes.
- Support layout options without guessing switch positions.
- Pilot one exact Mode or Keychron board with stock VIA firmware.
- Defer automatic catalog download until provenance/licensing/update policy is
  approved.

### V2-4 — OpenRGB live Lighting Studio

- Implement a minimal version-negotiated client or approved dependency for a
  separately installed local OpenRGB server.
- Import controller zones and matrix maps into canonical lighting geometry.
- Add explicit live playback start/stop, frame pacing, backpressure, disconnect
  recovery, and restore/leave-current policy.
- Never start the OpenRGB server, mutate a device, or claim persistence during
  discovery.
- Pilot one RGB board from the owner's hardware and prove per-LED order with a
  diagnostic corner/row pattern before animation playback.

### V2-5 — XAP/Drop research spike

- Read exact firmware identity from the owner's CTRL and ALT revisions.
- Establish supported XAP subsystem/version and upstream license facts.
- Build a read-only probe and fake protocol fixtures before any write.
- Decide whether XAP becomes a provider, requires optional firmware, or is
  unsupported on that revision. A spike may end in a documented no-go.

### V2-6 — Vendor and companion-firmware lane

- Only after the firmware-boundary ruling, decide whether proprietary adapters
  or an optional QMK companion module are justified.
- The application must never automate firmware flashing. Firmware installation
  instructions and artifacts require their own safety, recovery, provenance,
  and licensing plan.

### V2-7 — Public rebrand and v2 release

- Apply the approved public namespace set while preserving settled install
  identities and migration paths.
- Retarget AUR/Flatpak tooling before first registry publication.
- Update user-facing product scope without claiming universal compatibility.
- Run full repository verification, native builds and frozen smoke tests on all
  platforms, hardware qualification for every claimed pilot, signed release
  candidate verification, and only then the separately authorized `v2.0.0`
  release.

## Verification contract

- Repository entry point from `.agents/repo-guidance.md` passes every slice.
- Refactors prove existing tests still bite; new fixes/tests use red-green
  evidence where applicable.
- Fake HID/serial/OpenRGB servers cover discovery, timeouts, malformed data,
  disconnects, ambiguous identity, preflight refusal, and receipts without
  physical writes.
- Automated tests and smoke tests never write to keyboards.
- Hardware writes are manual GUI actions, exact device/capability matched,
  typed-confirmed, and recorded in a model/revision-specific qualification
  document.
- A board is listed publicly only for capabilities qualified on its exact
  model/revision/firmware. Family-wide claims require evidence that the family
  shares identity, protocol, geometry, and limits.
